# 状态、Todo 与 Git 约定

用于持续排障、装维设计、变更、窗口收尾和交接。这里规定语义与完成条件，不规定固定文档模板。

## 1. 当前状态只有一个权威入口

优先沿用项目已有的状态记录、任务系统、目录与命名。没有约定时，可由 `infra-init` 的默认骨架提供起点（见该入口的 `references/skeleton.md`），项目约定优先并可覆盖；存量项目只做语义到路径的映射，不搬迁文件。

持续排障、装维设计或任何变更需要让当前记录能回答：

- 当前目标和范围是什么；
- 关键事实何时、在哪个目标、通过什么来源核实；
- 做过哪些高影响决策，依据和谁确认的是什么；
- 哪些风险已被接受，由谁接受，适用边界是什么；
- 哪些动作已完成、部分完成或未验证；
- 证据保存在哪里，哪些是可重生成观测、哪些是不可替代记录；
- 当前 todo、阻塞、负责人和下一步是什么。

文档是当前事实的权威声明，机器是当前事实的来源。历史窗口、旧快照和 Git 历史提供演变证据，不与“当前入口”竞争。宿主或记忆工具生成的会话检查点文件是 agent 临时状态，应保持被忽略，不替代状态入口。

## 2. Todo 是工作索引，不是第二份日志

非琐碎任务始终维护 todo list：宿主提供专用工具时使用工具，否则维护项目内文件。条目围绕阶段与完成条件组织，保留并行项的真实状态，不复制每条命令和大段输出。

文件型 todo 沿用项目任务文件约定；其入库与否由该项目对过程记录的审计需求决定。阶段结束及时更新，交接时将未决项转成有目标、有负责人、有下一动作的记录。状态权威已经包含这些语义时，不再创建一份会漂移的平行清单。

## 3. Git 先管理服务状态与决策

被运维项目默认纳入需要 diff、回溯和追责的当前状态与关键决策。运行手册、窗口记录和复盘是否扩张入库，按项目的审计价值、维护成本与凭据策略决定。

原始命令输出、日志和可重生成清单默认保存在项目约定的观测位置，正文只摘必要结果与口径。不可替代证据需要受控保存时，记录其位置、保留责任和访问边界，不把 Git 当作任意大文件的默认收容所。

Git 仓库是版本化声明，不是多机同步机制，也不会把历史快照变成机器实况。服务器上的配置与脚本以现场为准，工作区副本需要同步时应有独立校验。

## 4. 初始化与提交都有明确边界

项目没有 Git 时，先展示拟管理的路径、将排除的内容和初始化影响，取得授权后再做本地初始化。只读问答不为了遵循本约定而自动创建仓库。

用户授权 Git 工作流后，agent 可对完整语义变更做本地原子提交：

- 一个提交只做一件可独立回滚的事；
- 使用中文约定式提交信息；
- 暂存前核对精确路径，提交前检查 staged diff，避免夹带日志、凭据或无关文件；
- 提交后独立读取实际入库清单与状态，而不只依赖命令退出码。

远端 push、删除远端内容、历史改写和其他远端副作用始终另行说明并授权。明文凭据的保存方式遵循目标项目的功能与策略，不把某个项目的偏好推广成普遍规则；公开开源仓库则默认保持敏感现场材料不纳入文件与历史。

## 5. 交接以新读者可行动为验收

交接前对照当前 todo 和目标，收敛已完成、部分完成、未验证与未开始事项。新读者不翻聊天记录也应能：

1. 找到当前状态权威与最后一次核实时间；
2. 理解关键决策和已接受风险；
3. 找到证据或知道如何重新生成；
4. 从未决 todo 的下一动作继续；
5. 识别哪些写操作仍需授权、哪些高敏资产需要人执行。

完成标准：状态、决策、风险和未决项只有明确的权威位置，todo 与之一致，已授权的本地原子提交真实反映了相关文件，且没有未说明的远端动作。
